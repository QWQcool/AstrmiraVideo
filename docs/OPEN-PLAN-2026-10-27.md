## 1. 即梦的"多参考"是怎么做的（实测反推）

### 1.1 数据模型：参考关系不是节点属性，而是**边**

从画布 React Tree 取到的真实对象（34 节点 / 45 边）：

```jsonc
// 节点：只有"当前展示的产物"，没有 references 字段
{
  "id": "node_jpt9r6ew6n",
  "type": "video",                 // image | video
  "position": { "x": -153.55, "y": 764.60 },
  "width": 568.889, "height": 320,
  "data": {
    "source": "model_generated",   // uploaded | model_generated
    "title": "视频 1",
    "resourceId": "59770617-…",             // 当前展示的那一个产物
    "resourceBatches": [                    // 一次生成出的多结果
      { "id": "edd16e2f-…", "resourceIds": ["59770617-…"] }
    ],
    "totalResourceCount": 1,
    "renderMode": "compact",
    "tagPresentation": { "tagIds": [] }
  }
}

// 边：多参考就是这个 —— 同一个 target 可以有多条
{
  "id": "edge_c372ew17bv",
  "source": "node_nzm31kqdrw",
  "target": "node_wpb6tz3p0a",
  "sourceHandle": "default",
  "targetHandle": "default",
  "type": "reference",          // ← 语义就是 "reference connection"
  "selectable": true,
  "ariaLabel": "Reference connection from 图片 node: 图片节点 4 (12).png to 图片 node: 图片 5"
}
```

**三条硬结论**：
1. 参考集合 = **入边集合**。实测扇入分布：1 条 → 7 个节点、2 条 → 6 个、3 条 → 6 个、**4 条 → 2 个**；最多 4 个素材喂一个生成节点。
2. 边里**没有角色**（无 first-frame / reference-image 之类字段），也**没有顺序**；`sourceHandle/targetHandle` 恒为 `default`。
3. 节点只存"当前展示的 `resourceId`"，历史结果靠 `resourceBatches[]`；这是他们的"版本"。

### 1.2 "首帧/尾帧/全能参考"放哪？—— 放在**生成模式 + 模型能力**里

前端 i18n 与校验字符串（取自 `zh-Hans` chunk）：

- `video_omni_ref` = **全能参考**
- `video_omni_reference_image_ref` = **引用参考**（"选择主体参考，可增强视频生成的参考效果"）
- `video_omni_reference_min` = **请至少上传 1 个素材**
- `video_omniref_max_cnt_pic` = **最多使用 {N} 个参考图片**
- `…model_reference_video_total_duration_message` = **已添加的参考视频总时长超过 {N} 秒，无法使用该模型**
- `…reference_resource_unavailable_message` = **参考素材不可用，请移除或替换**
- 内部还有 `referenceSlotId`（快照克隆要求"调用方持有参考槽位身份"）

即：**画布只表达"这几个素材属于这个节点"；能不能用、能用几个、能否混类型，由所选模型的元数据裁决**，不满足就**阻止提交并说明原因**，不静默丢素材。

**视频（全能参考，1 参考，4s）**：

```jsonc
{
  "initial": { "node_id": "node_mze5xj4fms", "submit_id": "eea58efe-…",
    "items": [{
      "resource_id": "5ba19232-…", "type": 2,
      "commerce_selection": { "benefit_type": "seedance_20_pro_720p_output" },  // 计费档位
      "reference_sources": [{ "material_idx": 0, "node_id": "node_h11rxvrbwq", "resource_id": "b4872d12-…" }],
      "params": { "video_params": {
        "mode": 4,                          // 实测「全能参考」= 4
        "model_name": "seedance_2.0_vip", "resolution": "720p",
        "aspect_ratio": "16:9", "duration_ms": 4000,
        "materials": [{ "type": 2, "image_uri": "tos-cn-i-…/62023978…" }],   // 视频侧不带 role
        "meta_list": [                      // ★ 视频侧用 meta_list 表达"素材在文中的位置"
          { "type": 1, "text": "…整段提示词…" },
          { "type": 2, "material_idx": 0 }
        ],
        "prompt": "…"
      }}
    }]}
}
```

**字段语义（实测，非推断）**：

| 字段 | 含义 | 证据 |
|---|---|---|
| `items[].type` | 1=图片，2=视频 | 两次采样 |
| `initial.submit_id` | 幂等键（重复提交同键只入队一次） | 每次生成一个新 UUID |
| `items[].resource_id` | **产物 id 由客户端预分配**，生成完成后它才成为资源 | ack 里原样返回该 id |
| `reference_sources[].material_idx` | 该素材在 `materials[]` 里的下标（**顺序**） | 4 条边 → idx 0..3 |
| `reference_sources[].node_id` | 来源节点（画布溯源） | 与入边 source 一致 |
| `image_params.materials[].role` | 图片素材角色（实测值 3） | 仅图片侧有 |
| `video_params.mode` | 生成模式，**实测「全能参考」= 4** | 面板文案对照 |
| `image_params.mode` | **实测图片参考生图 = 2** | 面板无模式文案，按 4 参考判定 |
| `commerce_selection.benefit_type` | 计费档位标识（`seedance_20_pro_720p_output`） | 视频侧才有 |
| `meta_list` vs `{{image:N}}` | **两套共存**：图片把素材引用内联在 prompt 的 `{{image:N}}`；视频用 `meta_list` 的 `{text}` + `{material_idx}` 分段 | 两次采样差异 |
| `metric` | 埋点：`upload_material_array` + `quote_node_array` | 字符串化 JSON |

**未采样**：首尾帧 / 智能多帧 / 智能编辑 / 超长视频的 mode 值；`role` 的其他取值；视频能否混音频素材。这些不做推断。
**成本实测**：图片 2K + 4 参考 = **8 积分**；视频 720p / 4s / 全能参考 = **56 积分**（81 → 73 → 17）。视频档比图片贵一个数量级，"多做实验"必须先算账。

### 1.4 对我们的含义

| | 即梦 | 我们 |
|---|---|---|
| 参考关系存放 | 边（集合，无角色无顺序） | `edge.role` + `draft.references` |
| 多参考 | 天然支持（N 条入边） | 图片节点只允许 1 张 `reference-image`；视频 1 首帧 + 1 尾帧 + 1 参考视频 |
| 用途语义 | 靠"生成模式"互斥档，画布上不可见 | 写在边上，可解释、可审计 |
| 代价 | 无法表达"第几帧""按什么顺序" | 表达不了 N 参考 |

**建议的最小改动（不换范式）**：`CanvasReferenceSchema` **已有 `order: 0..64`**，只是校验把 `reference-image` 卡在 1 张。放开到 N（按 `order` 排序）+ 在能力层声明 `maxReferenceImages / 允许类型 / 参考视频总时长`，即可在不引入"生成模式"的前提下支持多参考；首尾帧继续用有位置语义的 role。

**抓包后的新证据**：即梦提交层的 `reference_sources[].material_idx`（顺序）+ `materials[].role`（角色）与我们 `references[].order` + `references[].role` 是 **1:1 同构** —— 也就是说我们的数据模型本来就装得下多参考，卡住的只是校验上限。**不需要改成"边即集合"那套**。
**前置条件**：N9（主体/场景/风格角色语义）与 ComfyUI 多图模板 —— 否则就是"有按钮没能力"。这正是 S10-M1 / B111 挂起的原因。

### 1.5 决策：走 B 路线（生成模式），图/视频节点都允许多图，上限 9

**用户拍板（2026-10-27）**：按即梦那套"生成模式"组织参考，图片节点与视频节点都允许多张参考图，**上限 9 张**（比即梦界面提示的 12 少 3 张）。

**为什么这不是"重新规划"**——三个零件早就在仓库里，只是没接到画布上：

| 已有 | 位置 | 现状 |
|---|---|---|
| `settings.referenceMode: 'none' \| 'first-last-frame' \| 'omni-reference'` | `packages/shared/src/canvasDoc.ts` | 字段在，画布侧几乎没消费 |
| `ModelCapability.maxReferences / referenceModes / referenceKinds` + `checkCapability()` | `packages/shared/src/modelCapability.ts` | **只被创作草稿用**，画布完全没接线 |
| 参考 `order: 0..64` | `canvasDoc.ts` 的 `CanvasReferenceSchema` | 字段在，`canvasLineage.ts` 把 `reference-image` 硬编码成 1 张 |

**需要新增/改动的只有四处**：
1. `canvasLineage.ts`：容量判定从"硬编码 1 张"改成"按 `referenceMode` + `maxReferences`"；
2. 画布侧读能力目录：现在画布根本不看 `ModelCapability`，要接上（否则 9 张是拍脑袋，不是模型真的支持）；
3. provider：ComfyUI 从"上传一张 + 静态模板"扩到"上传 N 张 + 按 N 动态拼 `ReferenceLatent` 链"；
4. UI：模式切换 + 素材条（N 张、排序、移除、超限阻止）。

**P2/P3/P4 不返工**：动态工作流 + 多输入这套基建，正好是 P2（超清/扩图/局部重绘）要用的（它们也是"图进图出 + 额外参数"）。P3 分组、P4 预览都不碰这块。

**B 路线新出现的四个真问题（都要先验再落）**：

1. **9 张在 10GB 卡上跑不跑得动**：每多一张多一次 `VAEEncode` + 一次条件拼接。我们只验过 2 张（12.1s/张，预热后）。P1-2b 必须先测 4 张 / 9 张的耗时与显存，**跑不动就把上限按实测下调并如实写进能力目录**，不能既写 9 又跑不了。
2. **能力目录的真值从哪来**：ComfyUI 没有"这个模型支持几张参考"的元数据。只能让**模板自己声明**（新增 sidecar 字段，例如 `maxReferences`），否则 9 是产品愿望不是模型事实。
3. **提示词提及机制**：即梦图片侧把素材内联进 prompt（`{{image:N}}`），视频侧用 `meta_list` 分段；我们画布没有任何提及语法。参考到 3 张以上时，"哪张管人物、哪张管场景"只靠顺序会说不清 —— 要不要在画布补一个提及/锚点语法，属于产品决策（不在 P1-2a 顺手做）。
4. **`referenceMode` 与 `role` 的合法组合**：建议冻结为 `none`（无参考）/ `first-last-frame`（≤1 首 + ≤1 尾，位置语义）/ `omni-reference`（1..9 张 `reference-image`，`order` 定槽位）；互斥组合**阻止提交并说明**，不静默丢素材（沿 B93 纪律）。

### P1-1 双参考图模板与实验 · 已完成

**产物**：
- `deploy/comfyui-templates/experiments/flux2-klein-t2i-ref2.api.json`（+ `.meta.json`）：两张图各走 `LoadImage → VAEEncode`，两条 `ReferenceLatent` 串联（`cond → ref1 → ref2`），其余与内置 Klein t2i 同构。
- 放在 `experiments/` 子目录：模板扫描只读目录第一层的 `*.api.json`，所以**不会被生产自动挑中**（provider 目前只上传一张图，直接挂上去就是"有按钮没能力"）。
- `scripts/multiref-experiment.mjs`：固定 seed / 提示词 / 尺寸，跑 A（单参考）/ A+B / A+B₂ 三组，产出 PNG + workflow JSON + `results.json`。

**实验条件**：FLUX.2 Klein 4B distilled，4 步 / CFG 1，1024×576，seed 12345；
A = 即梦《故乡》的「妈妈 (1)」人物三视图；B = 「小院子」（雪院）；B₂ = 「卧室」（室内）；
提示词固定为「电影感剧照，人物站在画面中央，全身入画，实拍质感，自然光，浅景深」（**不提场景**，所以背景变化只能归因于参考图）。

| 组 | 参考 | 结果 | 证据 |
|---|---|---|---|
| run1 | A | 人物=酒红高领毛衣/中年女性（与 A 一致）；背景=林荫道（**与 B/B₂ 无关**） | [run1-A-only.png](assets/multiref-2026-10-27/run1-A-only.png) |
| run2 | A + B | 同一人物；背景变成**雪覆盖的农村平房院子**，连俯视构图都跟着 B | [run2-A+B.png](assets/multiref-2026-10-27/run2-A%2BB.png) |
| run3 | A + B₂ | 同一人物；背景换成**格子床单的卧室**（衣柜/推拉门/护墙板都在） | [run3-A+B2.png](assets/multiref-2026-10-27/run3-A%2BB2.png) |

**结论（只到这个强度）**：两条 `ReferenceLatent` 串联在两个不同参考上**确实都被消费**——第一张管人物，第二张管场景，换掉第二张场景随之改变。所以"多参考"在模板层可行，不需要换模型。

**如实边界**：
- 只跑了 1 个 seed、1 组提示词，**没有统计稳定性**；没有测 3 张以上、图文混排、参考之间互相矛盾（如提示词说室内而 B 是雪地）的情况；
- 冷启动成本高：首次进入（权重 15.2GB / 显存 10.7GB，动态换入换出）单张 **504s**；预热后 **12.1s/张**。生产必须有"首次慢"的预期管理，不能拿 12s 当承诺；
- run1 的 1.5s 是 **ComfyUI 命中缓存**（与先那次冷启动是同一份 workflow/seed），不是重算；
- 这只是"模板层通了"，**provider 仍只上传一张图**，产品还没支持多参考 —— P1-2 才接线。
